# Web Console 首次配置检查单

本文面向第一次打开 `/console/` 的部署者，说明配置页为什么显示“需要完成配置”，以及按什么顺序补齐必备项才能让本地预检通过并进入正常运行态。

检查单只覆盖“消除徽章、完成首次启动”所需的最小配置；联网搜索、天气、语音、RSS、Todo 提醒、知识库等能力可以之后再按需开启。

## 先理解这个徽章

- “需要完成配置”来自一次**整份候选配置的启动预检**，不是单字段校验。候选配置由当前受管 `runtime.toml`、SQLite 中的加密 secret、`.env` / 进程环境兜底和默认值共同组成。
- 未通过时，配置快照中的字段会共享同一个未通过结果，所以页面看起来“很多字段都未通过”是预期现象，不需要逐个字段去改。
- 页面顶部的“校验配置”只执行与正式启动一致的本地预检，不发起外部网络请求，也不会指出具体失败项。
- 徽章通过只代表保存后的候选配置满足启动条件；要让服务真正进入运行态，还需要重启。

预检需要同时满足三类条件：

1. Core 配置能按正式启动规则解析成功；
2. Gateway 至少有一个**启用且凭证完整**的平台入口；
3. `agent.toml` 中每条文本模型路线的候选中，至少有一个**已启用且有凭证**的 Provider。

## 最短路径

选择当前实际使用的入口，按下表补齐即可：

| 部署方式 | 必须完成 |
| --- | --- |
| 只用 QQ 官方机器人 | 模型 Provider 凭证 + QQ AppID 与 AppSecret |
| 只用 OneBot 11 | 模型 Provider 凭证 + 启用 OneBot 11 + Access Token |
| 只用微信服务号 | 模型 Provider 凭证 + 启用微信服务号 + Token（明文模式） |

如果同时使用多个入口，任一入口出现不完整凭证都会导致 Gateway 预检失败。

## 逐项检查

### 1. 模型与供应商：至少一个可用凭证

进入“模型与供应商”，为至少一个模型服务填入 API Key。

- 默认 Agent 模板的 `private_main`、`group_main` 和 `aux` 路线都同时包含 `openai`、`gemini`、`mimo`、`deepseek` 候选，因此通常填入其中任意一个供应商的 Key 就能通过。
- 预检要求的是“**每条路线**至少有一个可用候选”。如果改过路线，只配置一个不在该路线候选中的供应商仍然会失败。
- 关闭某个供应商的启用开关后，它的 Key 不再参与预检；但路线中只要还引用该供应商，预检就会失败，改路线时要同步移除对应候选。
- 自定义 Provider 必须先在 `agent.toml` 的 `[providers.*]` 中声明，并让对应环境变量名有真实凭证。
- 密钥保存后不会回传原文；输入框留空表示不修改，清除必须使用明确的清除动作。

### 2. 平台接入：至少一个入口完整

进入“平台接入”，按实际平台补齐。以下入口只要启用一个并通过校验，就满足 Gateway 条件。

**QQ 官方机器人**

- `QQ_BOT_APP_ID` 与 `QQ_BOT_APP_SECRET` 必须**同时存在**；只配置其中一个会直接判定为错误配置。
- `platform.qq_official.enabled` 默认为开启；未绑定凭证时不会被视为可用入口，也不会阻止使用其他入口启动。

**OneBot 11**

- 默认关闭。启用后必须填写 Access Token，否则启动预检失败。
- 确认绑定地址、端口和 WebSocket 路径与 NapCat 侧一致；这些参数不完整或路径非法同样会失败。

**微信服务号**

- 默认关闭。启用后必须填写 Token。
- AES 模式还必须填写 AppID 和合法的 EncodingAESKey（43 字符 Base64）；AppSecret 用于主动发送，不影响首次启动预检。
- 回调路径必须以 `/` 开头。

### 3. 文本模型路由：确认路线仍然可用

进入“文本模型路由”，检查 `agent.toml` 中的模型路线。

- 首次启动会自动生成默认 Agent 模板，通常无需修改。
- 每条路线至少保留一个可用候选；候选引用的 Provider 必须已声明且凭证可用。
- 被显式禁用的模型不能被任何保存的路线引用，包括候选链中的非首项。

### 4. 保存并校验

配置页底部的操作顺序：

1. 点“保存普通配置”提交启停开关、地址、端口等普通字段；
2. 点“保存密钥变更”提交 API Key、Token、AppSecret 等敏感字段；
3. 点“校验配置”确认本地预检结果。

首次启动处于 `setup_required` 时可以分步保存：字段本身合法、但其他域尚未补齐的配置仍然可以落盘，页面会继续显示“需要完成配置”，方便中断后继续。

### 5. 重启并确认

点“重启服务”，重新登录后检查：

- 配置页徽章显示“本地预检通过”，且“无待重启变更”；
- 总览页“服务健康”显示“健康”；
- `GET /healthz` 返回 `"state": "ready"`。

徽章可能在重启前就变为通过，因为它是按已保存的候选配置计算的；总览和 `/healthz` 反映的是当前进程真正加载的配置，所以必须重启后才能确认。

## 常见卡点

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| 仍是“需要完成配置” | 至少一类预检条件未满足 | 按本文顺序检查，或使用下文的排查入口 |
| 保存密钥后仍不通过 | Provider 被停用，或路线未引用该 Provider | 启用供应商，或把路线候选改为已配置的供应商 |
| QQ 入口校验失败 | 只填了 AppID 或 AppSecret | 补齐另一项，或同时清空两项 |
| OneBot 入口校验失败 | 启用后没有 Access Token | 填写 Token 或关闭入口 |
| 微信入口校验失败 | 缺少 Token；AES 模式缺 AppID / AESKey；AESKey 长度或格式不合法 | 补齐字段并确认 AESKey 为 43 字符 |
| 模型路线校验失败 | 路线没有可用候选，或引用了未声明的自定义 Provider | 补充凭证、声明 Provider，或调整候选 |
| 改了 `.env` 但页面值没变 | 同名字段已在控制台保存，受管值优先 | 以配置页当前值为准，或显式移除受管值 |
| 徽章已通过但总览仍“等待首次配置” | 尚未重启，进程仍在使用旧配置 | 重启服务并重新登录 |

## 定位失败项

配置页不会指出具体失败项，可以按以下顺序排查：

1. **启动日志**：以 `setup_required` 启动时，日志会输出分项结果：
   - `core_config_valid`：Core 配置是否解析成功；
   - `gateway_config_valid`：Gateway 配置是否解析成功；
   - `gateway_channel_enabled`：是否至少有一个完整入口；
   - `provider_preflight_valid`：Provider 路线与凭证是否可用。
2. **只读预检**：在运行目录执行

   ```bash
   qq-maid-bot config check
   ```

   重点看 `core_preflight=` 与 `gateway_preflight=`。如果实例尚未初始化或数据库 migration 未完成，命令会输出 `startup_preflight=not_run`，这属于只读保护，不是配置失败。
3. **来源盘点**：执行 `qq-maid-bot config sources` 查看每个字段当前来自环境、受管 TOML、加密 secret 还是默认值。
4. **运行态**：访问 `GET /healthz` 查看 `state` 与 `ready`。

更完整的配置来源、优先级和敏感值边界见[配置中心设计与字段清单](../development/config-center.md)。

## 判定标准

以下三项同时满足即可认为首次配置完成：

- 配置页显示“本地预检通过”，且没有待重启变更；
- 重启后总览页显示“健康”；
- 实际使用的平台入口能够收到并回复消息。

真实 API Key、AppSecret、Token、EncodingAESKey、群号和 openid 不要写入文档、日志或公开仓库。
